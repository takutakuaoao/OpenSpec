<a id="explore-first"></a>
# まず探索する

**`/opsx:explore` はあなたの思考パートナーです。問題はあるけれどまだ計画がない、というときはいつでも活用してください。** コードベースを調査し、選択肢をあなたと一緒に比較検討し、本当に望んでいることを明確にします。これらはすべて、コードを1行も書く前に行われます。全体像がはっきりしたら、`/opsx:propose` に引き継ぎます。

このドキュメントから1つだけ習慣を持ち帰るなら、これにしてください。**迷ったら、提案する前に探索する。**

その理由はこうです。AI コーディングアシスタントは積極的です。曖昧に頼むと、自信満々に*何か*を作ってくれますが、それが必要なものとは限りません。探索はその解決策です。あなたと AI が一緒に正しい次の一手を見つけ出す、リスクのない会話であり、提案する頃には正しいものを提案できる状態になっています。

<a id="when-to-explore"></a>
## いつ探索するか

探索は、思われている以上に、最初の一歩として適切な場面が多くあります。次のいずれかに当てはまるときに使いましょう。

- *問題*はわかっているが、*解決策*がわからない。（「ページが遅い気がする」「認証まわりがぐちゃぐちゃ」「注文が重複して作成されてしまう」）
- 複数のアプローチから選ぶ必要があり、実際のコードに照らしたトレードオフを整理してほしい。
- コードベースに慣れておらず、変更する前に仕組みを理解する必要がある。
- 要件が曖昧で、決める前に明確にしたい。
- 作業が見た目よりも大きい、あるいは小さいのではないかと感じていて、正直に見積もりたい。

探索を省略してよいのは、何がしたいのか、どうやるのかを正確に把握している場合だけです。その場合は、直接 [`/opsx:propose`](commands.md#opsxpropose) に進んでください。

<a id="what-it-does-and-doesnt"></a>
## できること（とできないこと）

探索は**会話**であり、ジェネレーターではありません。

**できること:**
- コードベースを読み、検索して、現実的な疑問に答える。
- 選択肢を比較し、それぞれのトレードオフを明示する。
- 設計をわかりやすくするための図を描く。
- 漠然としたアイデアを、具体的で実装可能なスコープに絞り込む手助けをする。
- あなたが頼んだとき、または提案を受け入れたときに、探索内容を記録する。`openspec new change` で変更の骨組みを作成し、指定した計画用の成果物を書き込むか、既存の変更の成果物を更新します。
- 準備ができたら `/opsx:propose` に移行する。

**できないこと:**
- コードの作成や変更。探索は、記録の場合も含め、どの経路でもコードを書きません。
- スキーマやテンプレートの設計・編集。これらを形作るのは思考ではなく変更です。
- 自分から変更を開始したり、成果物を書いたりすること。あなたが頼むか、提案に対して承諾しない限り何も書かず、書く場合も合意した内容と、変更の開始に必要なセットアップファイル（後述）だけです。
- 記録するようにあなたを促すこと。考えがまとまったときに提案はしますが、決めるのはあなたです。

これが要点です。探索にはコストがかからず、あなたが決めるまでは何も確定しません。行き止まりを3つ探索し、それぞれから何かを学んでから、生き残った道を提案できます。

<a id="its-already-installed"></a>
## すでにインストール済みです

朗報です。`/opsx:explore` は、デフォルトの**コア**プロファイルに `propose`、`apply`、`update`、`sync`、`archive` と並んで含まれています。何かを有効にする必要はありません。プロジェクトで OpenSpec がセットアップされていれば、AI チャットで探索をすぐに使えます。（すべての `/opsx:*` コマンドと同様に、ターミナルではなくアシスタントのチャットに入力します。[コマンドの仕組み](how-commands-work.md) を参照してください。）

<a id="a-full-example"></a>
## 完全な例

漠然とした不安が、明確で実装可能な変更になる様子をご覧ください。

```text
You: /opsx:explore

AI:  何を探索しますか？

You: チェックアウトで、ときどき注文が重複して作成されます。原因もわからないし、
     安全に直す方法もわかりません。

AI:  チェックアウトの経路を調べてみます...
     [注文サービス、決済 webhook ハンドラー、クライアントの送信ロジックを読む]

     わかったことをお伝えします。重複が発生する経路は2つあります。

     1. クライアントが2回送信する場合（ダブルクリック、遅いネットワークでの再試行）。
        現状、これを抑制する仕組みはありません。
     2. 決済 webhook が複数回発火し、ハンドラーがそのたびに注文を作成する場合。
        冪等性キーがありません。

     原因 #2 が危険なものです。二重に課金され、二重に出荷される可能性があります。

     修正方法は3つあり、堅牢性の高い順に並べるとおおよそ次のとおりです。
     - 注文作成エンドポイントに冪等性キーを導入する（両方の原因に対応）
     - webhook で payment-intent id による重複排除を行う（#2 のみ対応）
     - クライアント側のデバウンス（#1 のみ対応で、本当のバグは覆い隠される）

     すでにコードが payment-intent id を保存しているため、冪等性キーのアプローチは
     小さな変更で最大の効果が得られます。これでスコープを整理しましょうか？

You: はい、冪等性キーでいきましょう。

You: /opsx:propose add-order-idempotency-key

AI:  openspec/changes/add-order-idempotency-key/ を作成しました。先ほどの調査結果に
     基づく提案とデルタ仕様が入っています。実装の準備ができました。
```

何が起きたかに注目してください。出発点は「何かがおかしいが、手を付けるのが怖い」でした。20秒の探索で、それは名前の付いた根本原因、順位付けされた3つの選択肢、既存のコードに結びついた推奨案、そして明確な変更へと変わりました。続く提案が的確なのは、先に考える作業が行われているからです。

<a id="handing-off-to-propose"></a>
## 提案への引き継ぎ

探索は、何かにアーカイブされるわけではありません。準備ができたら、単に変更を開始すれば、AI が会話の文脈を成果物に引き継ぎます。

```text
explore  ──►  propose  ──►  apply  ──►  archive
 (考える)      (合意する)    (構築する)   (記録する)
```

「これを変更にしましょう」のように普通の言葉で伝えることも、`/opsx:propose <name>` を直接実行することもできます。どちらの場合でも、直前に行った探索が提案の土台となり、使い捨てのチャットで終わりません。

会話を離れずに、探索に変更そのものを記録させることもできます。「これで変更を開始して」と言えばフォルダの骨組みが作られ、「提案も書いて」と言えば、指定した成果物だけが書かれます。骨組みを作る際には、変更自身のメタデータも用意され、プロジェクトに不足しているトップレベルのもの（`openspec/specs/`、`openspec/changes/archive/`、`config.yaml`）も補われます。

行き先は引き継ぎの場合と同じですが、1つ違いがあります。propose はスキーマが実装に到達するために必要な成果物一式をすべて書きますが、記録は、あなたが指定した成果物だけを書きます。

拡張コマンドセットを使っている場合、探索は `/opsx:new` に引き継ぐこともでき、成果物を一つずつ作成できます。[ワークフロー](workflows.md) を参照してください。

<a id="tips-for-a-good-exploration"></a>
## 良い探索のコツ

- **解決策ではなく、問題を持ち込む。** 「ログインが遅い気がする」なら、AI は自由に調査できます。「Redis キャッシュを追加して」では、まだ検証していない答えを先に決めてしまうことになります。
- **トレードオフをはっきり尋ねる。** 「それぞれの選択肢の欠点は何？」と聞くと、より正直な比較が得られます。
- **まず読ませる。** 最良の探索は、AI が推測するのではなく、実際にコードを見ることから始まります。役立つなら、関連する場所を指し示してください。
- **途中でやめてもかまわない。** 探索の結果、そのアイデアに価値がないとわかれば、それは成功です。安く学べたのですから。
- **変更の途中でも再度探索する。** `/opsx:apply` の途中で行き詰まりましたか？ 一歩引いて、小さな問題を探索し、そのあと戻ることもできます。

<a id="the-honest-tradeoffs"></a>
## 正直なトレードオフ

**得られるもの:** 探索は、何も確定していない最も安価なタイミングで、方向違いを見つけられます。特に不慣れなコードでは威力を発揮し、AI がシステムを読んで要約してくれることで、午後いっぱいかかる調査の手間が省けます。

**かかるコスト:** 少しの忍耐です。探索は会話なので、`/opsx:propose` を勢いで実行して祈るよりも時間がかかります。すでに十分理解している作業なら、この追加ステップは単なるオーバーヘッドなので、省略してください。

目安としては、タスクが曖昧であるほど探索の効果は大きく、明確であるほど、直接提案に進んでかまいません。
