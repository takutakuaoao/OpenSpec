# 変更のレビュー

OpenSpec の約束はひとえに、あなたと AI が**コードを書く前に、何を作るのかを合意する**ことです。その合意が意味を持つのは、AI が下書きしたものを実際に読んだときだけです。このページは、それを行う2分間についてのものです。何を、どの順序で開き、何を見るべきかを説明します。

賭けの内容は単純です。1段落の計画の中で方向違いを見つけるのは、ほぼ無料です。同じ方向違いを300行のコードの中で見つけるのは、そうではありません。レビューは、その賭けの見返りを回収する場所です。

<a id="the-two-moments-you-review"></a>
## レビューする2つのタイミング

ちょうど2つあります。

```
/opsx:propose ──► 計画をレビュー ──► /opsx:apply ──► コードをレビュー ──► /opsx:archive
                  （コードを書く前）                  （/opsx:verify）
```

1. **`/opsx:propose`（または `/opsx:ff`）の後、`/opsx:apply` の前** — 計画がまだ言葉でしかないうちに読みます。
2. **構築後に `/opsx:verify` で** — コードが実際に計画どおりになっているかを確認します。

最初のレビューが最も多くを節約してくれますが、人が最も省略しがちなレビューでもあります。このページはそこに最も多くの時間を割いています。

<a id="read-it-in-this-order"></a>
## この順序で読む

変更は、`openspec/changes/<name>/` にあるプレーンな Markdown のフォルダです。何かがおかしいときに、最も早く切り上げられる順序でファイルを読んでください。

```
openspec/changes/add-dark-mode/
├── proposal.md      1. 意図とスコープ        ← これが間違っていたら、ここで止める
├── specs/…/spec.md  2. 要件                  ← レビューの核心
├── design.md        （大きな変更のみ）— 技術的なアプローチ
└── tasks.md         3. 作業計画
```

すべての行を読む必要はありません。ファイルごとに1つ、合計3つの質問に答えられれば十分です。

<a id="the-proposal-is-this-the-right-problem"></a>
## 提案: 正しい問題か？

最初に `proposal.md` を開きます。「なぜ」と「何を」、つまり意図、スコープ、アプローチが1〜2段落で書かれています。

**良い状態:** 明確な意図が1つ、見覚えのあるスコープ、そして今これを行う価値がある理由。

**危険信号:**

- あなたが頼んだものとは少し*違う*問題を解いている。
- スコープが膨らんでいる。テーマ切り替えを頼んだのに、提案が「ついでに」認証にも手を入れている。
- 曖昧である。「設定ページを改善する」はスコープではありません。「OS の設定に従うダークモード切り替えを追加する」ならスコープです。

**答えるべき質問:** *これは自分が実際に頼んだことと一致しているか、何かが紛れ込んでいないか？* 答えが「いいえ」なら、そこで止まります。先を読まずに、提案を修正してください（[差し戻しは低コスト](#pushing-back-is-cheap) を参照）。

<a id="the-spec-deltas-is-done-defined-correctly"></a>
## 仕様のデルタ: 「完了」は正しく定義されているか？

これがレビューの核心です。`specs/` 配下のデルタ仕様は、変更がリリースされたときに何が*真になる*かを、要件と、それを裏付けるシナリオとして記述します。

```markdown
## ADDED Requirements

### Requirement: Dark Mode Toggle
The system SHALL let a user switch between light and dark themes.

#### Scenario: Respects the OS preference on first load
- GIVEN a user who has never set a theme
- WHEN they open the app on a device set to dark mode
- THEN the app renders in dark mode
```

**良い要件の姿:** テスターに渡せる、明確な `SHALL`/`MUST` の文が1つあり、その文を実際に検証する GIVEN/WHEN/THEN のシナリオが少なくとも1つあること。

**危険信号:**

- **曖昧な要件。** 「システムは高速でなければならない（SHALL）」は、作ることもテストすることもできません。何が高速なのでしょうか？
- **シナリオのない要件**、あるいは、その下に置かれた要件をテストしていないシナリオ。
- **最も価値のある発見: 欠けているもの。** AI は、あなたが*言った*ことを忠実に書き留めます。あなたの役目は、*言い忘れた*ことに気づくことです。OS の設定に従うケースを最も重視していたのに、どのシナリオもそれに触れていないなら、それこそがレビューの見返りです。

デルタを読むときは、*システムがまさにこれだけを行ったら満足か？* と自問してください。ここにはまだコードに関するものは何もないので、変更は低コストのままです。

<a id="the-tasks-is-the-plan-of-work-sane"></a>
## タスク: 作業計画は妥当か？

最後に `tasks.md` を開きます。AI がこなしていく実装のチェックリストです。

**良い状態:** 順序立てられたステップで、それぞれが要件に紐づいており、不可解なものがない。

**危険信号:**

- 対応する要件のないタスク（これはどこから来たのか？）。
- すべての実質的な判断を隠してしまう、「機能を実装する」という巨大な1つのタスク。
- 承認したばかりのスコープの外にあるものに触れるタスク。

ここで見積もりをしたり、細かく管理したりするわけではありません。計画が、すでに受け入れた要件と一致していることを確認するのです。

<a id="pushing-back-is-cheap"></a>
## 差し戻しは低コスト

3つの質問のいずれかで答えが良くなかったなら、そう伝えてください。フェーズはなく、何もロックされていません。直して進めばよいのです。[変更の編集](editing-changes.md) と同様に、方法は2つあります。

- **自分でファイルを編集する。** プレーンな Markdown なので、スコープの行を変えたり、要件を引き締めたり、タスクを削除したりできます。
- **AI に何が問題かを伝えて**、修正させる: *「認証の変更は外して。スコープ外です」*、*「ユーザーがすでにテーマを選択している場合のシナリオを追加して」*、*「タスク3をスキーマと UI に分割して」*。

そして、変更した部分を読み直します。自分の名前で署名できる計画になるまで、書き直してください。そのやり取りこそが、プロダクトが機能している状態です。

<a id="after-the-code-verify"></a>
## コードの後: 検証

作業が実装されたら、`/opsx:verify` が2回目のレビューです。成果物とコードを再度読み込み、3つの観点で不一致を報告します。

| 観点 | チェック内容 |
|-----------|----------------|
| **完全性** | すべてのタスクが完了し、すべての要件が実装され、シナリオがカバーされているか |
| **正確性** | 実装が仕様の意図に一致し、エッジケースが処理されているか |
| **一貫性** | 設計上の判断が実際にコードに反映されているか |

```
You: /opsx:verify

AI:  add-dark-mode を検証しています...

     COMPLETENESS
     ✓ tasks.md の 8 個のタスクがすべてチェック済み
     ✓ specs のすべての要件に対応するコードがある
     ⚠ シナリオ "Respects the OS preference on first load" にテストカバレッジがない
```

問題は CRITICAL、WARNING、SUGGESTION に分類されて報告され、アーカイブを**ブロックしません**。不足点を明らかにして、判断はあなたに委ねます。これは、「AI がコードを書いたか」と「合意したものを作ったか」の違いです。

`/opsx:verify` は拡張プロファイルに含まれています。使えない場合は、`openspec config profile` で有効にする（その後 `openspec update` を実行する）か、変更と diff を自分で読み直してください。

<a id="right-size-the-review"></a>
## レビューを適切な規模にする

すべての変更に完全なチェックが必要なわけではありません。1ファイルの誤字修正なら、20秒でざっと見れば十分です。認証、決済、復旧できないデータに触れる変更には、上記のすべての質問が必要です。目的は儀式ではなく、ミスの代償が大きい場所に注意を向け、そうでない場所は流し読みすることです。

<a id="the-two-minute-checklist"></a>
## 2分間チェックリスト

- [ ] 提案の意図が、自分が頼んだ内容と一致している。
- [ ] スコープに余計なものが紛れ込んでいない。
- [ ] すべての要件が、テストできるほど具体的である。
- [ ] すべての要件に、それを実際に検証するシナリオがある。
- [ ] 最も重視しているケースがカバーされている。
- [ ] タスクが要件に対応しており、不可解なものやスコープ外のものがない。
- [ ] AI がまさにこれだけを作って、それ以上は何も作らなくても問題ない。

7つすべてを満たしたなら、自信を持って `/opsx:apply` を実行してください。1つでも満たさなければ、それは後退ではなく、2分間が役目を果たしたということです。
