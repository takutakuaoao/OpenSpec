# 変更の編集と反復

**変更に含まれるすべての成果物は、いつでも編集できる単なる Markdown ファイルです。** ロックされた「計画フェーズ」も、承認ゲートも、入るべき特別な編集モードもありません。実装を始めたあとで提案を変更したい？ `proposal.md` を開いて変更してください。実装の途中で設計が間違っていたと気づいた？ `design.md` を直して続けてください。これがすべての答えであり、意図された設計です。

このページは、「ちょっと待って、前の段階に戻って変更できる？」と思った瞬間のためのものです。はい、できます。よくあるケースごとにその方法を説明します。

<a id="two-ways-to-edit-anything"></a>
## 何でも2通りの方法で編集できる

次の両方を、いつでも使えます。

1. **ファイルを直接編集する。** 成果物は `openspec/changes/<name>/` 内のプレーンな Markdown です。`proposal.md`、`design.md`、`tasks.md`、または `specs/` 配下のデルタ仕様をエディタで開いて変更するだけで、他には何も必要ありません。

2. **AI に修正を依頼する。** チャットで、してほしいことをそのまま伝えます。「提案からキャッシュのアイデアを外して、レート制限のセクションを追加して」「設計はポーリングではなくキューを使うべき」など。AI は変更の他の部分を文脈として使いながら、成果物を編集します。

その場に合った方を使いましょう。ちょっとした言い回しの調整ならファイルを編集します。本質的な考え直しなら、AI に全体の文脈を踏まえて修正してもらいましょう。

<a id="how-do-i-update-the-proposal-or-specs-after-ive-started"></a>
## 「作業を始めたあとで、提案（や仕様）を更新するには？」

そのまま更新してください。同じ変更を洗練させるだけです。

拡張コマンドを使っている場合の自然な流れは、成果物を編集してから `/opsx:continue` を実行して新しい状態から再開するか、`/opsx:apply` を実行して更新された計画に沿って実装を続けることです。デフォルトの `core` コマンドを使っている場合は、成果物を編集して `/opsx:apply` を実行します。現在のファイルを読み込むので、成果物が今述べている内容に沿って構築されます。

考え方としては、成果物は署名された契約ではなく、生きた計画です。AI は常にその時点の内容に基づいて作業するため、成果物を編集すれば作業の舵を切れます。

```text
You: この変更のアプローチを変えたい。

You: [design.md を編集するか、AI に伝える:]
     design.md を、同期呼び出しではなくバックグラウンドジョブを使う内容に更新して。

AI:  design.md を更新しました。タスクリストはそのまま使えます。適用を続けますか？

You: /opsx:apply
```

これはよくある疑問への答えにもなっています。「提案を更新する」専用のコマンドがないのは、必要ないからです。ファイルが信頼できる唯一の情報源であり、それを（手作業でも AI 経由でも）編集することが更新です。

<a id="how-do-i-go-back-to-review-after-implementing"></a>
## 「実装したあとで、レビューに戻るには？」

「戻る」必要はありません。そもそも離れていないからです。ワークフローは流動的で、レビュー、編集、実装は、閉じ込められる順次のフェーズではありません。

具体的には、`/opsx:apply` で作業を進めたあと、次のことができます。

- 計画を見直したい？ 成果物を開いて読むか、ターミナルで `openspec show <change>` を実行して、まとまったビューを見ます。
- 変更すべき点を見つけた？ 成果物を編集して（または AI に依頼して）、続行します。
- コードが計画どおりかを体系的に確認したい？ `/opsx:verify`（拡張コマンド）を実行します。何もブロックせずに、完全性、正確性、一貫性を報告します。[ワークフロー: 検証](workflows.md#verify-check-your-work) を参照してください。

戻るべき「レビューフェーズ」はありません。レビューは、実装後を含め、いつでも行えるものだからです。

<a id="i-edited-the-code-by-hand-how-do-i-reconcile-that-with-openspec"></a>
## 「コードを手で編集しました。OpenSpec とどう整合させる？」

これは頻繁に起こることで、問題ありません。エディタで何かを調整した結果、コードと成果物が食い違っている状態です。どちらが正しいかに応じて、同期を取り戻します。

- **コードが正しく、仕様が古くなっている。** デルタ仕様（関係があればタスクも）を、実際にリリースした振る舞いを記述するように更新します。アーカイブは仕様を信頼できる唯一の情報源にマージするため、アーカイブの前に仕様を現実と一致させておく必要があります。
- **仕様が正しく、コードがずれている。** コードが仕様に一致するまで、実装または修正を続けます。

不一致を素早く洗い出すには `/opsx:verify` が便利です。成果物とコードを読み、どこが乖離しているかを教えてくれます。その出力を整合のための ToDo リストとして扱い、両者が一致したらアーカイブしてください。

原則: アーカイブの時点で、仕様は公式な真実の記録になります。したがって、アーカイブの前に、仕様がコードの実際の動作を正直に表すようにしてください。手動の編集は歓迎ですが、仕様がこっそり食い違わないようにしましょう。

<a id="refining-a-proposal-youre-not-happy-with"></a>
## 気に入らない提案を洗練する

生成された提案が的を外している場合、有効な手は3つあります。

- **その場で反復する。** 何がおかしいかを AI に伝え（「スコープが広すぎる、管理者向け機能は外して」）、修正させます。最も低コストで、たいていは正解です。
- **先に探索し、再提案する。** アイデア自体が不明確なことが問題なら、`/opsx:explore` に戻って考え抜き、そこからより鋭い提案を生み出します。[まず探索する](explore.md) を参照してください。
- **やり直す。** 意図が根本的に変わった場合は、古いものにパッチを当てるより、新しい変更の方が明確なことがあります。

最後の手段には専用の判断ガイドがあります。次の節をご覧ください。

<a id="when-to-update-vs-start-a-new-change"></a>
## 更新するか、新しい変更を始めるか

簡潔に言うと、**同じ作業を洗練させるなら更新し、意図が根本的に変わった場合やスコープが膨らんで別の作業になった場合は新しく始めます。**

- 目標は同じで、より良いアプローチがある？ 更新します。
- スコープの縮小（今は MVP をリリースし、残りは後で）？ 更新し、アーカイブし、フェーズ2用に新しい変更を作ります。
- 問題自体が変わった（「ダークモードの追加」が「完全なテーマシステムの構築」になった）？ 新しい変更にします。

完全なフローチャートと実例は [ワークフロー: 更新するか、やり直すか](workflows.md#when-to-update-vs-start-fresh) に、より詳しい解説は [OPSX: 更新するか、やり直すか](opsx.md#when-to-update-vs-start-fresh) にあります。

<a id="a-note-on-tasks"></a>
## タスクについての注意

`tasks.md` は固定された計画ではなく、生きたチェックリストです。実装しながら、見つけたタスクを追加したり、不要とわかったものを削除したり、並べ替えたりできます。AI は `/opsx:apply` の間、完了したものにチェックを付け、あとで戻ってきたときは最初の未チェックのタスクから再開します。途中でリストを編集するのは想定された使い方です。
