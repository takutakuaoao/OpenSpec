# チームでの OpenSpec

他のガイドの内容は、一人で使う場合でも20人のチームで使う場合でも同じように当てはまります。チームで変わるのは周辺の疑問です。仕様はどこに置くのか、チームメイトはどうやって計画をレビューするのか、そしてこれらは既存のプルリクエストのフローにどう組み込まれるのか。

端的に言えば、変更は単なるファイルであり、OpenSpec は git に一切触れません。そのため、既存のワークフローを置き換えるのではなく、そこに自然に収まります。このページでは、うまく機能する規約をまとめます。

<a id="one-rule-openspec-doesnt-touch-git"></a>
## 唯一のルール: OpenSpec は git に触れない

OpenSpec は `openspec/` 配下のプレーンな Markdown を読み書きするだけです。プロジェクトに対してコミット、ブランチ作成、プッシュ、プルを行うことはなく、[ストア](stores-beta/user-guide.md) を自動でクローンしたり同期したりすることもありません。つまり、次のようになります。

- **`openspec/` は他のソースと同様にコミットします。** 仕様、アクティブな変更、アーカイブはプロジェクト履歴の一部です。（はい、フォルダ全体をコミットしてください。[FAQ](faq.md#should-i-commit-the-openspec-folder-to-git) を参照してください。）
- **変更は、コードと同じようにバージョン管理するフォルダです。** `openspec/changes/add-dark-mode/` は、ブランチ上の単なるファイル群です。
- **以下はすべて規約であり、強制ではありません。** OpenSpec にこのやり方を強制されることはありません。ただ、自然に収まるというだけです。

<a id="the-everyday-loop"></a>
## 日々のループ

うまく機能するワークフローでは、1つの変更を1つのブランチとプルリクエストに対応させます。

```
git switch -c add-dark-mode        start a branch, as usual
   │
/opsx:propose add-dark-mode        draft the plan (proposal + specs + tasks)
   │
REVIEW THE PLAN                    you read it before any code — see Reviewing a Change
   │
/opsx:apply                        build it; artifacts + code change together
   │
git commit && open a PR            the PR contains the spec delta AND the code
   │
teammate reviews, merges
   │
/opsx:archive                      fold the delta into specs/, move the change to archive/
```

計画とコードは同じブランチ上に並んで存在するため、チームメイトは両方をまとめてレビューできます。そして半年後でも、アーカイブされた仕様がコードの現在の姿の理由を説明してくれます。

<a id="reviewing-specs-in-a-pull-request"></a>
## プルリクエストでの仕様レビュー

チームが効果を実感するのはここです。PR に変更のデルタ仕様が含まれていると、レビュアーは、生の diff では決して得られないものを手にします。それは、コードを1行も読む前に得られる、**この変更が何を実現するはずなのかについての平易な言葉による説明**です。

レビュアーにとって良いレビューの順序は次のとおりです。

1. **`proposal.md` を読む** — これは正しい問題とスコープか？
2. **`specs/` 配下のデルタを読む** — 「完了」の定義は正しいか？（これは [変更のレビュー](reviewing-changes.md) の2分間チェックを、PR の中で行うものです。）
3. **それからコードの diff を読む** — コードはまさにその要件を実現しているか？

*アプローチ*に異論があるレビュアーは、300行のコードをまたいで蒸し返すのではなく、提案に対して低コストでそれを伝えられます。デルタ仕様を PR 説明の冒頭近くに置くか、レビュアーに変更フォルダを案内して、そこから読み始めてもらいましょう。

<a id="when-to-archive"></a>
## アーカイブのタイミング

アーカイブでは、変更のデルタをメインの `openspec/specs/` に統合し、変更フォルダを `openspec/changes/archive/YYYY-MM-DD-<name>/` に移動します。`specs/` は**共有された信頼できる唯一の情報源**であるため、チームではタイミングが重要です。実用的な規約は2つあります。

- **PR のマージ後にアーカイブする（推奨）。** ブランチがアクティブな変更を保持し、メインブランチにマージされたらそこでアーカイブします（多くの場合、ごく小さなフォローアップコミットか定期的なクリーンアップで行います）。これにより、共有の `specs/` は、実際にリリースされた作業だけを反映して前進します。
- **PR の中でアーカイブする。** 小規模なチームにはこちらが簡単です。コードを追加するのと同じ PR で、同期とアーカイブも行います。トレードオフとして、`specs/` の diff とコードの diff が同時に入るため、PR がやや煩雑になることがあります。

どちらかを選び、一貫して使いましょう。どちらの場合でも、`/opsx:archive` はタスクが完了していることを確認し、最初に同期するかどうかを尋ねるため、中途半端な状態で誤ってマージされることはありません。

<a id="two-people-parallel-changes"></a>
## 2人での並行した変更

変更は別々のフォルダなので、衝突しません。

- **異なる変更を異なる人が担当する場合は問題ありません。** `add-dark-mode` と `rate-limit-login` は、異なるブランチ上の異なるフォルダです。両方がアーカイブされるまでは、互いに影響しません。
- **1つの変更に1人のオーナー。** 同じ変更フォルダを2人が編集すると、同じファイルを2人が編集した場合とまったく同じように衝突します。1つの変更の作者は1人にするか、変更を2つに分割してください（これも [適切なサイズにする](writing-specs.md#right-size-the-change) べき理由の一つです）。
- **衝突が現れるのは `specs/` だけです。** 2つの変更が*同じ*要件を変更している場合、2つ目をアーカイブすると `openspec/specs/…/spec.md` で衝突します。他のマージコンフリクトと同様に、現実を反映した要件を残して解決してください。これはまれなことであり、むしろ利点でもあります。システムがどう振る舞うべきかについて2つの変更の意見が食い違っていることを、git が教えてくれているのです。

<a id="when-planning-outgrows-one-repo"></a>
## 計画が1つのリポジトリに収まらなくなったとき

ここまでの内容は、計画がコードリポジトリ自身の `openspec/` フォルダにあることを前提としており、それが適切なデフォルトです。計画が本当に複数のリポジトリやチームにまたがる場合、たとえば1つの機能が3つのサービスに影響する場合や、あるチームが所有し他のチームが利用する要件がある場合に使うのが、ベータ版の**ストア**機能です。計画専用のリポジトリを用意し、どのコードリポジトリからでもそれを参照できます。まずは [ストアのユーザーガイド](stores-beta/user-guide.md) から始めてください。
