# 用語集

OpenSpec のすべての用語を、平易な言葉で1か所にまとめて定義します。一度ざっと目を通しておけば、他のドキュメントがより速く読めるようになります。

用語はトピックごとにグループ化され、各グループ内では英語の語のアルファベット順に並んでいます。

<a id="the-core-nouns"></a>
## 中核となる名詞

**仕様（Spec）。** システムの一部がどう振る舞うかを記述したドキュメントです。仕様は `openspec/specs/` にあり、ドメインごとに整理され、要件とシナリオで構成されます。仕様は、「このソフトウェアは何をするのか？」という問いに対する、合意された答えです。[概念](concepts.md#specs) を参照してください。

**信頼できる唯一の情報源（Source of truth）。** `openspec/specs/` ディレクトリ全体を指します。システムの現在の、合意された振る舞いを保持します。変更はこれに対する編集を提案し、アーカイブがそれを適用します。

**変更（Change）。** 作業の1単位で、`openspec/changes/<name>/` 配下のフォルダとしてまとめられます。変更には、その作業に関するすべてが含まれます。提案、設計、タスク、そしてそれが導入する仕様の編集です。1つの変更が、1つの機能または修正に対応します。

**成果物（Artifact）。** 変更の中にあるドキュメントです。標準の成果物は、提案、デルタ仕様、設計、タスクです。これらは依存関係の順に作成され、互いに情報を提供します。

**デルタ仕様（Delta spec）。** 変更の中にある仕様で、仕様全体を再度記述する代わりに、`ADDED`、`MODIFIED`、`REMOVED` のセクションを使って、何が変わるかだけを記述します。これにより、OpenSpec は既存システムをきれいに編集できます。[概念](concepts.md#delta-specs) を参照してください。

**ドメイン（Domain）。** 仕様の論理的なグルーピングで、`auth/`、`payments/`、`ui/` などです。システムについての考え方に合ったドメインを選びます。

<a id="inside-a-spec"></a>
## 仕様の内部

**要件（Requirement）。** システムが持たなければならない単一の振る舞いで、通常は RFC 2119 のキーワードを使って書かれます。「システムは、30分後にセッションを失効させなければならない（SHALL）。」要件は、*どのように*ではなく、*何を*を述べます。

**シナリオ（Scenario）。** 要件が実際に機能する様子を示す、具体的でテスト可能な例で、通常は Given/When/Then 形式です。シナリオによって要件が検証可能になります。1つのシナリオから自動テストを書くことができます。

**RFC 2119 キーワード。** MUST、SHALL、SHOULD、MAY という語で、要件がどれほど厳格かについての標準化された意味を持ちます。MUST と SHALL は絶対的です。SHOULD は推奨で、例外の余地があります。MAY は任意です。この名前は、これらを定義したインターネット標準文書に由来します。

<a id="the-artifacts"></a>
## 成果物

**提案（Proposal, `proposal.md`）。** 変更の*理由*と*内容*です。意図、スコープ、大まかなアプローチを記述します。最初に作成する成果物です。

**設計（Design, `design.md`）。** *どのように*です。技術的アプローチ、アーキテクチャ上の判断、変更が見込まれるファイルを記述します。単純な変更では任意です。

**タスク（Tasks, `tasks.md`）。** チェックボックス付きの実装チェックリストです。AI は `/opsx:apply` の間にこれを順に進め、完了したものにチェックを付けていきます。

<a id="the-lifecycle"></a>
## ライフサイクル

**アーカイブ（Archive）。** 変更を完了する行為です。デルタ仕様がメインの仕様にマージされ、変更フォルダは `openspec/changes/archive/YYYY-MM-DD-<name>/` に移動します。アーカイブ後は、仕様が新しい現実を記述するようになります。[概念](concepts.md#archive) を参照してください。

**同期（Sync）。** 変更をアーカイブ*せずに*、そのデルタ仕様をメインの仕様にマージすることです。通常は自動（アーカイブ時に提案されます）ですが、長期にわたる変更向けに `/opsx:sync` として単独でも使えます。[コマンド](commands.md#opsxsync) を参照してください。

<a id="workflow-and-commands"></a>
## ワークフローとコマンド

**OPSX。** 現在の標準的な OpenSpec ワークフローで、固定されたフェーズではなく、流動的なアクションを中心に構築されています。スラッシュコマンドはすべて `/opsx:` で始まります。[OPSX ワークフロー](opsx.md) を参照してください。

**スラッシュコマンド（Slash command）。** `/opsx:propose` のように、AI アシスタントのチャットに入力するコマンドです。スラッシュコマンドがワークフローを進めます。ターミナルのコマンドではありません。[コマンドの仕組み](how-commands-work.md) を参照してください。

**探索（Explore, `/opsx:explore`）。** 思考パートナーとなるコマンドです。コードベースを読み、選択肢を比較し、曖昧なアイデアを具体的な計画へと明確にします。コードは決して書かず、探索内容を変更として記録するよう頼んだとき、または提案に対して承諾したとき以外は、他に何も書きません。問題はあるがまだ計画がない場合の、推奨される出発点です。[まず探索する](explore.md) を参照してください。

**CLI。** ターミナルで実行する `openspec` プログラムです。プロジェクトのセットアップ、変更の一覧表示と検証、ダッシュボードの表示、アーカイブを行います。OpenSpec のターミナル側です。[CLI](cli.md) を参照してください。

**スキル（Skill）。** AI アシスタントが自動検出して従う、指示のフォルダ（`.../skills/openspec-*/SKILL.md`）です。スキルは、OpenSpec のワークフローをアシスタントに届けるための、新しく登場しつつあるツール横断の標準です。

**コマンドファイル（Command file）。** ツールごとのスラッシュコマンドファイル（`.../commands/opsx-*`）です。より古い提供方法で、スキルと並んで引き続きサポートされています。直接触れることはほとんどありません。

**プロファイル（Profile）。** プロジェクトにインストールされるスラッシュコマンドのセットです。**コア**（デフォルト）は `propose`、`explore`、`apply`、`update`、`sync`、`archive` です。**拡張**セットでは、`new`、`continue`、`ff`、`verify`、`bulk-archive`、`onboard` が加わります。`openspec config profile` で変更します。

**提供方式（Delivery）。** OpenSpec がツールに対して、スキル、コマンドファイル、またはその両方のうちどれをインストールするかです。グローバルに設定し、`openspec update` で適用します。

<a id="customization"></a>
## カスタマイズ

**スキーマ（Schema）。** ワークフローにどの成果物があり、それらが互いにどう依存するかの定義です。組み込みのデフォルトは `spec-driven`（proposal → specs → design → tasks）です。フォークしたり、独自に作成したりできます。[カスタマイズ](customization.md#custom-schemas) を参照してください。

**テンプレート（Template）。** スキーマ内の Markdown ファイルで、特定の成果物に対して AI が生成する内容を形作ります。テンプレートを編集すると、再ビルドなしで AI の出力がただちに変わります。

**プロジェクト設定（Project config, `openspec/config.yaml`）。** プロジェクトごとの設定です。デフォルトのスキーマ、すべての計画リクエストに注入される `context:`、成果物ごとの `rules:` があります。スタックや規約を OpenSpec に教える最も簡単な方法です。[カスタマイズ](customization.md#project-configuration) を参照してください。

**コンテキスト注入（Context injection）。** プロジェクトの背景情報を `config.yaml` の `context:` フィールドに記述して、AI が生成するすべての成果物に自動的に追加されるようにすることです。AI が別のファイルを読んでくれることを期待するより、確実です。

**依存関係グラフ（Dependency graph）。** 成果物の `requires:` の関係によって形成される有向グラフです。DAG（有向非巡回グラフ。矢印は前方にのみ向かい、ループしない）であり、OpenSpec はこれを使って次に何を作成できるかを判断します。

**関門ではなく手段（Enablers, not gates）。** 成果物の依存関係は、次に何が*必要か*ではなく、次に何が*可能になるか*を示す、という原則です。どの成果物も、いつでも見直して編集できます。[コア概念の概要](overview.md#enablers-not-gates) を参照してください。

<a id="coordination-across-repos-beta"></a>
## リポジトリをまたぐ調整（ベータ）

これらの用語は、計画が複数のリポジトリにまたがる場合にのみ関係します。ベータ版であり、ほとんどのユーザーは無視して構いません。[ストアのユーザーガイド](stores-beta/user-guide.md) を参照してください。

**ストア（Store）。** 計画のみを役割とする、独立したリポジトリです。すでにご存じの `openspec/` の構成（仕様と変更）に、小さな識別ファイルが加わったものです。マシン上に名前を付けて一度登録すれば、どこからでも任意の OpenSpec コマンドをその中で実行できます。

**参照（Reference）。** コードリポジトリの `openspec/config.yaml` における、そのリポジトリが利用するストアの宣言です。参照は読み取り専用です。リポジトリは自身のルートを保持し、`openspec instructions` には、参照先ストアの仕様のインデックスが加わります。各仕様には、それを取得するための正確なコマンドが付いています。

**作業コンテキスト（Working context）。** `openspec context` が、現在のリポジトリについて組み立てるものです。そのリポジトリの OpenSpec ルートと、参照するすべてのストア、およびそれぞれの取得方法です。「今、何を扱っているのか？」への答えです。

**ワークセット（Workset）。** 一緒に開く、個人用でマシンローカルなフォルダの集合です（ストアと、作業対象のコードリポジトリなど）。`openspec workset create` で明示的に作成します。これらのローカルパスに関する情報が、共有の計画リポジトリにコミットされることはありません。
