# 既存プロジェクトでの OpenSpec の利用

**始めるために、コードベース全体をドキュメント化する必要はありません。これから変更する部分についてだけ、仕様を書きます。** これは、既存プロジェクトに OpenSpec を導入するうえで最も重要なポイントであり、OpenSpec がブラウンフィールドを第一に考えて作られている理由です。

よくある心配は、こんな感じです。「うちのアプリは8万行もの歴史がある。OpenSpec が役に立つようになるまでに、そのすべての仕様を書かなければならないのか？」いいえ。そんなことは嫌でしょうし、私たちもそうです。OpenSpec は、変更ごとに少しずつ仕様を育てます。最初の変更は、それが触れる部分を文書化し、次の変更はその部分を文書化し、数か月かけて、実際に行う作業の周りに自然に仕様が埋まっていきます。

このガイドでは、大がかりな作業をせずに初日から始める方法を紹介します。

<a id="the-thirty-second-version"></a>
## 30秒でわかる流れ

```bash
$ cd your-existing-project
$ openspec init          # openspec/ と、お使いの AI ツール用のコマンドを追加する
```

その後、AI チャットで次を実行します。

```text
/opsx:explore            # 任意: 変更する領域を AI に読ませる
/opsx:propose <実際に必要な、小さな変更>
/opsx:apply
/opsx:archive
```

これで仕様は、その変更が触れたシステムの部分を正確に記述するようになり、それ以上のことは記述しません。それで正しいのです。残りの8万行について悩む必要はもうありません。

<a id="why-delta-first-is-the-whole-trick"></a>
## デルタファーストがすべての秘訣である理由

OpenSpec の変更は**デルタ**として書かれます。`ADDED`、`MODIFIED`、`REMOVED` です。デルタは、システム全体ではなく、現在の振る舞いに対して何が変わるかを記述します。

これはまさにブラウンフィールドの作業が求めているものです。ゼロから作ることはめったにありません。フィールドを追加する、リダイレクトを直す、タイムアウトを短くする、といった作業が中心です。デルタを使えば、周辺のすべてについて40ページの仕様を先に書くことなく、その1つの変更を正確に仕様化できます。

そのため、`openspec/specs/` ディレクトリは、最初から充実しているわけではありません。ほぼ空の状態から始まり、蓄積されていきます。アーカイブされた変更ごとに、そのデルタがマージされます。`auth/` の仕様が充実するのは、認証まわりの変更をいくつか行ったあとであり、それはまさに充実させたいタイミングです。

より詳しい仕組みについては、[概念: デルタ仕様](concepts.md#delta-specs) を参照してください。

<a id="your-first-change-on-a-real-codebase"></a>
## 実際のコードベースでの最初の変更

小さくて実際に必要なものを選んでください。おもちゃでも、書き直しでもありません。どのみち今週行うつもりだった変更です。小さな最初の変更は、低リスクでワークフローを教えてくれます。

**ステップ1: AI に関連する領域を読ませる。** 不慣れな、あるいは大規模なコードベースで `/opsx:explore` が真価を発揮するのはここです。これから触れる部分を指定し、何かを提案する前に、仕組みを把握させます。

```text
You: /opsx:explore

AI:  何を探索しますか？

You: 公開 API にレート制限を追加する必要があるのですが、リクエストが現在
     ミドルウェアをどう流れているのかよくわかりません。

AI:  たどってみます... [ルーター、ミドルウェアスタック、設定を読む]
     リクエストは Express に入り、認証ミドルウェアを通過してから、
     コントローラーに渡されます。現状、レート制限のレイヤーはありません。
     最もきれいな挿入ポイントは、認証の直後にあるミドルウェアです。
     スコープを整理しましょうか？
```

AI があなたの実際の構造を理解したので、作成する提案は、汎用的なテンプレートではなく、あなたのコードに合ったものになります。大規模なコードベースでは、この習慣が最も多くの苦労を減らしてくれます。[まず探索する](explore.md) を参照してください。

**ステップ2: 変更を提案する。** 提案とそのデルタ仕様は、この変更だけを記述します。

```text
You: /opsx:propose add-api-rate-limiting
```

**ステップ3: 構築してアーカイブする。** 他の変更と同様に、`/opsx:apply` と `/opsx:archive` を使います。アーカイブ後には、どのみち必要だった変更から生まれた、レート制限の振る舞いに関する本物の仕様が手に入ります。

<a id="prefer-a-guided-tour-use-onboard"></a>
## ガイド付きツアーがお好みなら onboard を使う

自分のコードで、ナレーション付きでループ全体が進行する様子を見たいなら、拡張コマンドの `/opsx:onboard` がまさにそれを行います。コードベースをスキャンして小さく安全な改善点を見つけ、それを提案、実装、アーカイブする過程を、各ステップを説明しながら案内します。

まず、拡張コマンドを有効にします。

```bash
$ openspec config profile      # 拡張ワークフローを選択する
$ openspec update              # このプロジェクトに適用する
```

その後、チャットで次を実行します。

```text
/opsx:onboard
```

実際のプロジェクトでの最もやさしい導入であり、残しても破棄してもよい、本物の（小さな）変更が手元に残ります。[コマンド: `/opsx:onboard`](commands.md#opsxonboard) を参照してください。

<a id="but-i-already-have-requirements-docs"></a>
## 「でも、すでに要件ドキュメントがあります」

PRD、SRS、正式な仕様書、場合によっては TLA+ モデルをお持ちかもしれません。結構です。それらを丸ごとインポートする必要はありませんし、捨てる必要もありません。

既存のドキュメントは、変換すべき仕様ではなく、**探索のための素材**として扱ってください。変更を始めるときに、関連するセクションを貼り付けるか AI に指し示し、そこから焦点を絞った OpenSpec のデルタを作らせます。デルタは、今変更しようとしている振る舞いを、OpenSpec のテスト可能な要件とシナリオの形式で記述します。元のドキュメントは、背景資料としてそのまま残ります。

正直な理由: OpenSpec の仕様は、意図的に振る舞い優先で、変更単位にスコープが限定されています。40ページの PRD は、役割の異なる別の成果物です。一度に一括変換しようとすると、誰も信頼しない、大きくて古い仕様ができがちです。実際の変更から仕様を育てるほうが、正確に保てます。

```text
You: /opsx:explore
You: これはチェックアウトに関する PRD のセクションです。次に
     「ゲストチェックアウト」の要件を実装します。
     [関連する要件を貼り付ける]
AI:  [読み込み、確認の質問をしてから、変更のスコープ整理を手伝う]
You: /opsx:propose add-guest-checkout
```

<a id="organizing-specs-in-a-big-codebase"></a>
## 大規模なコードベースで仕様を整理する

仕様は `openspec/specs/` の下に、**ドメイン**ごとにグループ化されて置かれます。ドメインとは、チームがシステムについて考える方法に合った、論理的な領域です。最初から分類体系全体を設計する必要はありません。その領域での最初の変更が必要としたときに、ドメインのフォルダを作成すれば十分です。

ドメインの一般的な分け方:

- **機能領域ごと:** `auth/`、`payments/`、`search/`
- **コンポーネントごと:** `api/`、`frontend/`、`workers/`
- **境界づけられたコンテキストごと:** `ordering/`、`fulfillment/`、`inventory/`

新しく来た人がうなずけるものを選んでください。あとで改良できます。[概念: 仕様](concepts.md#specs) を参照してください。

<a id="monorepos-and-work-that-spans-repos"></a>
## モノレポと、複数のリポジトリにまたがる作業

モノレポでは、最もシンプルなモデルは、リポジトリのルートに `openspec/` ディレクトリを1つ置き、パッケージやサービスに対応するドメインを設けることです。これでほとんどのチームに対応できます。

作業が本当に**複数のリポジトリ**（または、別々のものとして扱う複数のパッケージ）にまたがる場合、OpenSpec にはベータ版の**ストア**機能があります。計画を独立した専用のリポジトリに置き、あなたのどのコードリポジトリからも参照できるため、計画を1つのリポジトリの `openspec/` フォルダ内に置く必要がありません。ベータ版なので、そのコマンドや状態は変化していくものとして扱ってください。まずは [ストアのユーザーガイド](stores-beta/user-guide.md) で、考え方と最小限の有用な手順を確認してください。

<a id="a-few-honest-cautions"></a>
## いくつかの正直な注意点

- **すべてを後から埋めたくなる衝動に抵抗する。** 変更しないコードの仕様を書くのは生産的に感じますが、たいていはそうではありません。そうした仕様は、現実に追従させる仕組みがないため、古くなります。実際の変更に仕様を牽引させましょう。
- **初期の変更は小さく保つ。** 最初のいくつかの変更は、リリースと同じくらい、リズムを学ぶためのものです。スコープを絞れば、ループが速く回り、学びが安く済みます。
- **`openspec/` を git にコミットする。** 仕様とアーカイブは、それが記述するコードと並んでバージョン管理下に置くべきです。
- **AI に文脈を与える。** 強い規約を持つ大規模なコードベースでは、`openspec/config.yaml` の `context:` を記入して、すべての提案があなたのスタックとパターンを尊重するようにしましょう。[カスタマイズ](customization.md#project-configuration) を参照してください。
