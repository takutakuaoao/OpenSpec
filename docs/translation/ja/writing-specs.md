# 良い仕様の書き方

仕様を白紙から書くことはめったにありません。変更を普通の言葉で説明すると、`/opsx:propose` が要件とシナリオを下書きし、そのあとであなたがそれを良いものに仕上げます。このページは、その最後の部分について説明します。「良い」とはどのような姿か、そして AI をそこへ導くにはどうすればよいか。

これは [変更のレビュー](reviewing-changes.md) の対になるものです。レビューは下書きの弱点を見つけることであり、書くことは、強い仕様が何でできているかを知ることです。

<a id="a-spec-is-behavior-not-code"></a>
## 仕様は振る舞いであり、コードではない

仕様は、システムが*何をするか*を、誰でも確認できる言葉で述べるものであり、どう作られているかではありません。**要件**（振る舞いの記述）と**シナリオ**（それを裏付ける具体例）で構成されます。

```markdown
### Requirement: Session Timeout
The system SHALL expire a session after 30 minutes of inactivity.

#### Scenario: Idle timeout
- GIVEN an authenticated session
- WHEN 30 minutes pass with no activity
- THEN the session is invalidated and the user must re-authenticate
```

*どのように*実現するか、つまりキュー、ライブラリ、テーブルスキーマなどは `design.md` かコードに置いてください。振る舞いと実装が1つの要件に混ざると、その要件はテストできなくなり、コードが変わった途端に古くなっていきます。

<a id="what-makes-a-good-requirement"></a>
## 良い要件とは

良い要件とは、1つの振る舞いを、他の誰かにテストを任せられるほど平易に述べたものです。

- **1つの文に、1つの `SHALL`/`MUST`。** 要件に「さらに」という節が3つあるなら、それは実際には3つの要件です。分割してください。
- **観測可能であること。** コードの外にいる人が、それが成り立っているかどうかを判断できなければなりません。「システムは、アップロードが10 MBを超えたときにエラーバナーを表示しなければならない（SHALL）」は観測可能です。「システムは、大きなアップロードを適切に処理しなければならない（SHALL）」は観測できません。
- **適切な強さ。** OpenSpec は RFC 2119 のキーワードを使用しており、それぞれ意味が異なります。

  | キーワード | 意味 |
  |---------|---------|
  | `MUST` / `SHALL` | 絶対的な要件。交渉の余地なし。 |
  | `SHOULD` | 強い推奨。正当な理由があれば例外も許される。 |
  | `MAY` | 本当に任意。 |

  デフォルトでは `MUST`/`SHALL` を使いましょう。`SHOULD` は、本当に「よほどの理由がない限り」という意味のときだけ使います。

要件のテスト: *コードを一度も見たことのないテスターが、それが合格したかどうか判断できるか？* できないなら、もっと明確にする必要があります。

<a id="what-makes-a-good-scenario"></a>
## 良いシナリオとは

シナリオは、要件が真価を発揮する場所です。それぞれが、自動テストになりうる具体的な GIVEN / WHEN / THEN です。

- **要件を実際に検証している。** 要件を言い換えて繰り返しただけのシナリオは、何もテストしていません。特定の状況と特定の結果を持つものにしてください。
- **正常系だけでなく、重要なケースを網羅する。** 有効なログインは簡単です。空の入力、期限切れのトークン、2回目のクリック、うまくいかない事態。バグが潜むのはそういう場所であり、シナリオの価値が最も高い場所です。
- **タイトルでケースを示す。** 「Scenario: Rejects an expired token」はレビュアーに何がカバーされているかが一目でわかりますが、「Scenario: Test 2」ではわかりません。

役に立つ習慣: 承認する前に、*壊れていたら一番困るケースは何か？* と自問し、それを名指しするシナリオがあることを確認してください。

<a id="pick-the-right-kind-of-delta"></a>
## 適切な種類のデルタを選ぶ

変更は、仕様への編集を3種類のセクションで記述します。正しいものを使うことで、アーカイブされた仕様が正確に保たれます。

- **`## ADDED Requirements`** — これまで存在しなかった、まったく新しい振る舞い。
- **`## MODIFIED Requirements`** — すでに存在し、変更される振る舞い。新しいバージョンの全文を含めてください。何が変わったかの短いメモがあると、レビュアーの助けになります。
- **`## REMOVED Requirements`** — なくなる振る舞い。理由を1行添えます。

アーカイブ時には、ADDED はメインの仕様に追加され、MODIFIED は古いバージョンを置き換え、REMOVED は削除されます。ある機能（capability）の最後の要件を削除すると、その機能は廃止されます。中身が空の仕様を残す代わりに、アーカイブは `openspec/specs/<capability>/spec.md` を削除します。これはアーカイブの中でファイルを削除する唯一のステップであるため、明示的に要求する必要があります。変更の `.openspec.yaml` に、そのファイルがすでに必要としている `schema:` と並べて `retire_capabilities: true` を追加してください。これがなければ、アーカイブは中断し、その旨を知らせます。廃止はファイル全体を削除するため、仕様にタイトル、`## Purpose`、要件ブロック以外のもの（`## Notes` セクションや、要件の下のコメントなど）が含まれている間は、拒否されます。中断時には該当する行が示されるので、それらを `## Purpose` か要件に移すか、仕様を手動で削除してください。呼び出し元のチェックアウト内にある仕様については、アーカイブの出力に、コミット済みのファイルを復元する `git checkout` も示されます。選択されたストアには、代わりにチェックアウト単位の復旧ガイダンスが提供されます。実際には存在する要件を ADDED としてマークすると、競合する要件が2つできてしまいます。新しい振る舞いを MODIFIED として記述すると、置き換える対象がありません。迷ったら、現在の仕様を開いて、その要件がすでに存在するかどうかを確認してください。

知っておく価値のあるセクションがもう1つあります。まだ存在しない機能（capability）をデルタが作成する場合は、`## Purpose` で始めてください。その機能が何のためのものかを1〜2文で記します。アーカイブは、作成するメインの仕様の Purpose としてこれを使用します。省略すると、手動で埋める `TBD` のプレースホルダーが入ります。既存の仕様にはすでに Purpose があるため、デルタの Purpose は無視されます。変更するには `openspec/specs/<capability-path>/spec.md` を直接編集してください。ここでの `<capability-path>` は `specs/` からの相対ディレクトリで、フラットな構成のプロジェクトでは `user-auth`、ドメインごとに整理されたプロジェクトでは `identity/user-auth` のようになります。

<a id="right-size-the-change"></a>
## 変更を適切なサイズにする

仕様を書く際の最もよくある間違いは、言い回しの悪い要件ではなく、3つの変更になろうとしている変更です。

**良い変更には、一文で言える意図が1つあります。** 「ダークモード切り替えを追加する」「ログインエンドポイントにレート制限をかける」「セッションを Cookie から移行する」。変更の説明に「さらに」が多く必要なら、それは分割すべきというサインです。

変更が大きすぎるサイン:

- 提案のスコープが、無関係な機能の羅列のように読める。
- レビューに午後いっぱいかかるため、誰もレビューしない。
- 2人が衝突せずに作業することができない。
- タスクの半分は、それだけで単独でリリースできる。

小さな変更ほどレビューしやすく、集中した1回のセッションで構築しやすく、アーカイブしか残っていない半年後に理解しやすくなります。複数の変更を並行して進めることはいつでもできます。[変更の編集と反復](editing-changes.md) と [ワークフロー](workflows.md) を参照してください。

逆のことも起こります。1行の誤字修正に、3つの要件と設計ドキュメントは必要ありません。儀式の重さは、リスクの大きさに合わせてください。

<a id="how-to-steer-the-ai-toward-a-good-draft"></a>
## AI を良い下書きに導く方法

最初の下書きは `/opsx:propose` が作成するため、返ってくるものの品質は、与えるものの品質に比例します。要件を手で書く必要はなく、AI に狙いをうまく定めればよいのです。

- **意図と境界を述べる。** *「初回ロード時に OS の設定に従うダークモード切り替えを追加して。既存のテーマ API には触れないで。」* スコープ外の半分は、スコープ内の半分と同じくらい重要です。
- **気にしているケースを挙げる。** *「ユーザーがすでに手動でテーマを選択している場合のシナリオを必ず入れて。」* AI は、あなたが指し示したものをカバーします。
- **それから編集する。** プレーンな Markdown です。曖昧な `SHALL` を引き締め、何もテストしていないシナリオを削除し、抜けていたケースを追加する。あるいは AI に頼みます。*「タイムアウトの要件が曖昧なので、30分に固定して。」*

下書き、洗練、繰り返し。これを数回行うと、信頼できる仕様ができあがります。それがすべての目的です。

<a id="a-quick-checklist"></a>
## 簡易チェックリスト

- [ ] 各要件が、`SHALL`/`MUST` を伴う、観測可能な1つの振る舞いである。
- [ ] 要件に実装の詳細が組み込まれていない。
- [ ] すべての要件に、それを実際に検証するシナリオが少なくとも1つある。
- [ ] 正常系だけでなく、重要なエッジケースやエラーケースにもシナリオがある。
- [ ] デルタが、現在の仕様に対して ADDED / MODIFIED / REMOVED を正しく使っている。
- [ ] 変更全体に、一文で言える意図が1つだけある。
