<a id="commands"></a>
# コマンド

OpenSpec のスラッシュコマンドのリファレンスです。これらのコマンドは、AI コーディングアシスタントのチャットインターフェース（Claude Code、Cursor、Devin Desktop など）で呼び出します。

ワークフローのパターンと、各コマンドをいつ使うべきかについては、[ワークフロー](workflows.md) を参照してください。CLI コマンドについては、[CLI](cli.md) を参照してください。

これらのページでは、正式な名前として `/opsx:<command>` を使用しています。ツールによって
表記が異なる場合があります。Cursor と GitHub Copilot は `/opsx-propose` を登録し、Codex は
`$openspec-propose` を使用するため、お使いのツールについては [呼び出し方](supported-tools.md#how-to-invoke)
を確認してください。OpenSpec が生成するファイルは、すでに正しい形式を使用しています。

<a id="quick-reference"></a>
## クイックリファレンス

<a id="default-quick-path-core-profile"></a>
### デフォルトのクイックパス（`core` プロファイル）

| コマンド | 目的 |
|---------|---------|
| `/opsx:propose` | 変更を作成し、計画用成果物を1ステップで生成する |
| `/opsx:explore` | 変更を決める前にアイデアを考え抜く |
| `/opsx:apply` | 変更のタスクを実装する |
| `/opsx:update` | 変更の計画用成果物を修正し、整合性を保つ |
| `/opsx:sync` | デルタ仕様をメイン仕様にマージする |
| `/opsx:archive` | 完了した変更をアーカイブする |

<a id="expanded-workflow-commands-custom-workflow-selection"></a>
### 拡張ワークフローのコマンド（カスタムワークフロー選択）

| コマンド | 目的 |
|---------|---------|
| `/opsx:new` | 新しい変更の骨組みを開始する |
| `/opsx:continue` | 依存関係に基づいて次の成果物を作成する |
| `/opsx:ff` | ファストフォワード: すべての計画用成果物を一度に作成する |
| `/opsx:verify` | 実装が成果物に一致していることを検証する |
| `/opsx:bulk-archive` | 複数の変更を一度にアーカイブする |
| `/opsx:onboard` | ワークフロー全体を通したガイド付きチュートリアル |

デフォルトのグローバルプロファイルは `core` です。拡張ワークフローのコマンドを有効にするには、`openspec config profile` を実行してワークフローを選択し、プロジェクトで `openspec update` を実行します。

## コマンドリファレンス

<a id="opsxpropose"></a>
### `/opsx:propose`

新しい変更を作成し、計画用成果物を1ステップで生成します。これは `core` プロファイルでのデフォルトの開始コマンドです。

**構文:**
```text
/opsx:propose [change-name-or-description]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name-or-description` | いいえ | ケバブケースの名前、または平易な言葉による変更の説明 |

**動作:**
- `openspec/changes/<change-name>/` を作成する
- 実装の前に必要な成果物を生成する（`spec-driven` の場合: proposal、specs、design、tasks）
- 変更が `/opsx:apply` の準備ができた時点で停止する

**例:**
```text
You: /opsx:propose add-dark-mode

AI:  openspec/changes/add-dark-mode/ を作成しました
     ✓ proposal.md
     ✓ specs/ui/spec.md
     ✓ design.md
     ✓ tasks.md
     実装の準備ができました。/opsx:apply を実行してください。
```

**ヒント:**
- 最も速いエンドツーエンドの経路として使う
- 成果物をステップごとに制御したい場合は、拡張ワークフローを有効にして `/opsx:new` + `/opsx:continue` を使う

<a id="opsxexplore"></a>
### `/opsx:explore`

> **迷ったらここから始めましょう。** 探索は、リスクなしで使える思考パートナーです。コードベースを読み、選択肢を比較し、曖昧なアイデアを、コードを書く前に具体的な計画へと磨き上げます。デフォルトのプロファイルに含まれています。詳しい説明とその他の例については、[まず探索する](explore.md) ガイドを参照してください。

変更を決める前に、アイデアを考え抜き、問題を調査し、要件を明確にします。

**構文:**
```
/opsx:explore [topic]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `topic` | いいえ | 探索または調査したい内容 |

**動作:**
- 構造を必要としない、探索的な会話を開始する
- コードベースを調査して質問に答える
- 選択肢やアプローチを比較する
- 考えを明確にするための図を作成する
- あなたが頼んだとき、または提案に対して承諾したときに、探索内容を記録する: `openspec new change` で変更の骨組みを作成し、指定した計画用成果物を書き込むか、既存の変更の成果物を更新する
- 洞察がまとまったら、`/opsx:propose`（デフォルト）または `/opsx:new`（拡張ワークフロー）に移行できる

**例:**
```text
You: /opsx:explore

AI:  何を探索しますか？

You: モバイルアプリの認証はどう扱うべきでしょうか？

AI:  現在の認証のセットアップを調べてみます...
     [コードベースを分析する]

     Web アプリではセッションベースの認証を使っているようです。
     モバイルでは、主な選択肢が3つあります。

     1. JWT トークン（ステートレス、オフラインで動作）
     2. OAuth2（サードパーティログインが必要な場合）
     3. 現在のセッションを拡張する（よりシンプルだが、接続が必要）

     API にはすでに CORS が設定されています。どの方向に興味がありますか？

You: JWT でいきましょう。

AI:  それは残しておく価値のある判断です。add-jwt-auth という名前で変更を
     開始しましょうか？ 変更フォルダだけで、他にはまだ何も作りません。

You: はい。

AI:  openspec/changes/add-jwt-auth/ を開始しました。ご指示いただければ、
     今話し合った内容から提案、仕様、タスクを書きます。
```

**ヒント:**
- 要件が不明確な場合や、調査が必要な場合に使う
- コードは決して書かず、あなたが頼むか、提案に対して承諾しない限り何も書かない
- 決める前に複数のアプローチを比較するのに適している
- ファイルを読み、コードベースを検索できる

<a id="opsxnew"></a>
### `/opsx:new`

新しい変更の骨組みを開始します。変更フォルダを作成し、`/opsx:continue` または `/opsx:ff` で成果物を生成するのを待ちます。

このコマンドは拡張ワークフローセットの一部です（デフォルトの `core` プロファイルには含まれません）。

**構文:**
```
/opsx:new [change-name] [--schema <schema-name>]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | 変更フォルダの名前（指定しない場合は尋ねられる） |
| `--schema` | いいえ | 使用するワークフローのスキーマ（デフォルト: 設定または `spec-driven`） |

**動作:**
- `openspec/changes/<change-name>/` ディレクトリを作成する
- 変更フォルダに `.openspec.yaml` メタデータファイルを作成する
- 作成可能な最初の成果物のテンプレートを表示する
- 変更名とスキーマが指定されていない場合は尋ねる

**作成されるもの:**
```
openspec/changes/<change-name>/
└── .openspec.yaml    # 変更のメタデータ（スキーマ、作成日）
```

**例:**
```
You: /opsx:new add-dark-mode

AI:  openspec/changes/add-dark-mode/ を作成しました
     Schema: spec-driven

     作成可能: proposal
     作成するには /opsx:continue を、すべての成果物を作成するには /opsx:ff を使用してください。
```

**ヒント:**
- 説明的な名前を使う: `add-feature`、`fix-bug`、`refactor-module`
- `update`、`changes`、`wip` のような汎用的な名前は避ける
- スキーマはプロジェクト設定（`openspec/config.yaml`）でも設定できる

<a id="opsxcontinue"></a>
### `/opsx:continue`

依存関係の連鎖の中で、次の成果物を作成します。段階的に進められるよう、一度に1つの成果物を作成します。

**構文:**
```
/opsx:continue [change-name]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | 続行する変更（指定しない場合は文脈から推測される） |

**動作:**
- 成果物の依存関係グラフを照会する
- どの成果物が準備できていて、どれがブロックされているかを表示する
- 準備ができている最初の成果物を作成する
- 文脈のために依存先のファイルを読む
- 作成後に利用可能になるものを表示する

**例:**
```
You: /opsx:continue

AI:  Change: add-dark-mode

     成果物のステータス:
     ✓ proposal    (done)
     ◆ specs       (ready)
     ◆ design      (ready)
     ○ tasks       (blocked - needs: specs, design)

     specs を作成しています...

     [proposal.md を読み、要件に基づいて仕様を作成する]

     ✓ openspec/changes/add-dark-mode/specs/ui/spec.md を作成しました

     利用可能になりました: design
     次の成果物を作成するには、/opsx:continue を実行してください。
```

**ヒント:**
- 次に進む前に各成果物をレビューしたいときに使う
- 制御したい複雑な変更に適している
- 複数の成果物が同時に準備できることがある
- 作成された成果物は、続行する前に編集できる

<a id="opsxff"></a>
### `/opsx:ff`

成果物の作成をファストフォワードします。すべての計画用成果物を一度に作成します。

**構文:**
```
/opsx:ff [change-name]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | ファストフォワードする変更（指定しない場合は文脈から推測される） |

**動作:**
- 依存関係の順序ですべての成果物を作成する
- ToDo リストで進捗を追跡する
- `apply-required` なすべての成果物が完了した時点で停止する
- 次の成果物を作成する前に、各依存先を読み込む

**例:**
```
You: /opsx:ff add-dark-mode

AI:  add-dark-mode をファストフォワードしています...

     ✓ proposal.md を作成
     ✓ specs/ui/spec.md を作成
     ✓ design.md を作成
     ✓ tasks.md を作成

     すべての計画用成果物が完了しました！
     実装の準備ができました。開始するには /opsx:apply を実行してください。
```

**ヒント:**
- 何を作るかが明確に見えているときに使う
- わかりやすい変更では `/opsx:continue` より速い
- そのあとも成果物を編集できる
- 小〜中規模の機能に適している

<a id="opsxapply"></a>
### `/opsx:apply`

変更のタスクを実装します。タスクリストを順に進め、コードを書いて項目にチェックを付けます。

**構文:**
```
/opsx:apply [change-name]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | 実装する変更（指定しない場合は文脈から推測される） |

**動作:**
- `tasks.md` を読み、未完了のタスクを特定する
- タスクを1つずつ進める
- 必要に応じて、コードを書き、ファイルを作成し、テストを実行する
- チェックボックス `[x]` でタスクを完了としてマークする

**例:**
```
You: /opsx:apply

AI:  add-dark-mode を実装しています...

     tasks.md を読み込んでいます:
     - [ ] 1.1 Create ThemeContext
     - [ ] 1.2 Add CSS custom properties
     - [ ] 1.3 Implement localStorage persistence

     1.1 に取り組んでいます: ThemeContext の作成...
     [src/context/ThemeContext.tsx を作成する]

     ✓ 1.1 完了

     1.2 に取り組んでいます: CSS カスタムプロパティの追加...
     [src/styles/globals.css を更新する]

     ✓ 1.2 完了
     ...
```

**ヒント:**
- 中断された場合でも、中断したところから再開できる
- 変更名を指定することで、並行する変更に対して使える
- 完了状態は `tasks.md` のチェックボックスで追跡される

<a id="opsxupdate"></a>
### `/opsx:update`

変更の既存の計画用成果物を修正し、互いに整合性を保ちます。対象は計画用成果物のみで、コードを編集することはありません。

**構文:**

```text
/opsx:update [change-name]
```

**引数:**

| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | 更新する変更（指定しない場合は文脈から推測される） |

**動作:**

- `openspec status --change <name> --json` を通じて、変更の成果物を読み込む
- 依頼された修正を適用する。修正が指定されていない場合は、成果物の矛盾をレビューする
- 他の既存の成果物を、どの方向にも整合させる（設計の編集が提案にさかのぼって波及することもある）
- 書き込む前に、成果物ごとに1つずつ、すべての編集をあなたに確認する
- 次のステップを推奨して終了する: `/opsx:continue`（未着手の成果物）、`/opsx:apply`（修正した計画をコードに反映）、または `/opsx:archive`（すべて完了）

**欠落しているファイル:**

- `specs/**/*.md` のような glob 型の成果物で、少なくとも1つのファイルが存在する場合、update は欠落している関連ファイルを提案できます。スキーマの指示を使用し、作成する前に、具体的なパスの確認を求めます。
- まだファイルがない成果物は、`/opsx:continue` の担当のままです。意図的にスキップされた成果物には手を加えません。
- 新しいファイルは、変更ディレクトリの内側にとどまる必要があります。確認されたパスにファイルが作成前に出現した場合、update は上書きせずに停止します。

**例:**

```text
You: /opsx:update add-dark-mode - we're storing the theme in a cookie now, not localStorage

AI:  add-dark-mode の成果物を読み込んでいます...

     設計では localStorage が2か所で参照されています。タスク 1.3 は
     localStorage への永続化を扱っています。提案にはストレージへの言及がありません。

     修正案:
     1. design.md - localStorage の判断を Cookie ストレージに差し替える
     2. tasks.md - タスク 1.3 を Cookie への永続化に書き換える

     修正 1 を適用しますか？ (design.md)
```

**ヒント:**

- 既存のファイルがない成果物は開始しません。そのためには `/opsx:continue` を有効にするか、その任意のワークフローがインストールされていない場合は `openspec status` と `openspec instructions` を使ってください。
- 変更がすでに実装されている場合は、コードが修正後の計画に合うよう、続けて `/opsx:apply` を実行する
- 修正によって変更の*意図*が変わる場合は、代わりに新しい変更を一から始める（[更新するか、やり直すか](opsx.md#when-to-update-vs-start-fresh) を参照）

<a id="opsxverify"></a>
### `/opsx:verify`

実装が変更の成果物に一致していることを検証します。完全性、正確性、一貫性をチェックします。

**構文:**
```
/opsx:verify [change-name]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | 検証する変更（指定しない場合は文脈から推測される） |

**動作:**
- 実装品質の3つの観点をチェックする
- 実装の証拠をコードベースから検索する
- 問題を CRITICAL、WARNING、SUGGESTION に分類して報告する
- アーカイブをブロックしないが、問題を明らかにする

**検証の観点:**

| 観点 | 検証する内容 |
|-----------|-------------------|
| **完全性** | すべてのタスクが完了し、すべての要件が実装され、シナリオがカバーされている |
| **正確性** | 実装が仕様の意図に一致し、エッジケースが処理されている |
| **一貫性** | 設計上の判断がコードに反映され、パターンが一貫している |

**例:**
```
You: /opsx:verify

AI:  add-dark-mode を検証しています...

     COMPLETENESS
     ✓ tasks.md の 8 個のタスクがすべてチェック済み
     ✓ specs のすべての要件に対応するコードがある
     ⚠ シナリオ "System preference detection" にテストカバレッジがない

     CORRECTNESS
     ✓ 実装が仕様の意図に一致している
     ✓ シナリオのエッジケースが処理されている
     ✓ エラー状態が仕様の定義に一致している

     COHERENCE
     ✓ 設計上の判断がコード構造に反映されている
     ✓ 命名規則が design.md と一貫している
     ⚠ 設計では "CSS variables" とあるが、実装は Tailwind クラスを使っている

     SUMMARY
     ─────────────────────────────
     Critical issues: 0
     Warnings: 2
     Ready to archive: Yes (with warnings)

     Recommendations:
     1. システム設定の検出に対するテストを追加する
     2. design.md を Tailwind の使用に合わせて更新するか、CSS 変数を使うようリファクタリングする
```

**ヒント:**
- 不一致を早期に発見するために、アーカイブの前に実行する
- 警告はアーカイブをブロックしないが、潜在的な問題を示している
- コミットする前に AI の作業をレビューするのに適している
- 成果物と実装の間のずれを明らかにできる

<a id="opsxsync"></a>
### `/opsx:sync`

**任意のコマンドです。** 変更のデルタ仕様をメインの仕様にマージします。必要に応じてアーカイブが同期するかどうかを尋ねるため、通常は手動で実行する必要はありません。

**構文:**
```
/opsx:sync [change-name]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | 同期する変更（指定しない場合は文脈から推測される） |

**動作:**
- 変更フォルダからデルタ仕様を読み込む
- ADDED/MODIFIED/REMOVED/RENAMED のセクションを解析する
- 変更をメインの `openspec/specs/` ディレクトリにマージする
- デルタで言及されていない既存の内容を保持する
- 変更をアーカイブしない（アクティブなまま残る）

**例:**
```text
You: /opsx:sync

AI:  add-dark-mode のデルタ仕様を同期しています...

     読み込み: openspec/changes/add-dark-mode/specs/ui/spec.md
     対象:     openspec/specs/ui/spec.md

     適用する変更:
     ✓ ADDED: Theme Selection requirement (2 scenarios)
     ✓ ADDED: Accessibility requirement (1 scenario)

     マージしています...
     ✓ openspec/specs/ui/spec.md を更新しました

     変更はアクティブなままです。完了する準備ができたら /opsx:archive を実行してください。
```

**手動で使うタイミング:**

| シナリオ | sync を使うか？ |
|----------|-----------|
| 長期にわたる変更で、アーカイブの前にメインに仕様を反映したい | はい |
| 並行する複数の変更が、更新後のベース仕様を必要としている | はい |
| マージを個別にプレビュー/レビューしたい | はい |
| 小さな変更で、直接アーカイブに進む | いいえ（アーカイブが処理する） |

**ヒント:**
- 同期は単純なコピー＆ペーストではなく、賢く行われる
- 重複させずに、既存の要件にシナリオを追加できる
- 同期後も変更はアクティブなまま（アーカイブされない）
- ほとんどのユーザーは直接呼び出す必要がない。必要ならアーカイブが確認する

---

<a id="opsxarchive"></a>
### `/opsx:archive`

完了した変更をアーカイブします。変更を確定し、アーカイブフォルダに移動します。

**構文:**
```
/opsx:archive [change-name]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-name` | いいえ | アーカイブする変更（指定しない場合は文脈から推測される） |

**動作:**
- 成果物の完了状況をチェックする
- タスクの完了状況をチェックする（未完了の場合は警告）
- まだ同期されていない場合、デルタ仕様の同期を提案する
- 変更フォルダを `openspec/changes/archive/YYYY-MM-DD-<name>/` に移動する
- 監査証跡のために、すべての成果物を保持する

**例:**
```text
You: /opsx:archive

AI:  add-dark-mode をアーカイブしています...

     成果物のステータス:
     ✓ proposal.md が存在する
     ✓ specs/ が存在する
     ✓ design.md が存在する
     ✓ tasks.md が存在する (8/8 タスク完了)

     デルタ仕様: まだ同期されていません
     → 今すぐ同期しますか？（推奨）

You: はい

AI:  ✓ 仕様を openspec/specs/ui/spec.md に同期しました
     ✓ openspec/changes/archive/2025-01-24-add-dark-mode/ に移動しました

     変更が正常にアーカイブされました。
```

**ヒント:**
- 未完了のタスクがあってもブロックはしないが、警告する
- デルタ仕様は、アーカイブ中でも、その前でも同期できる
- アーカイブされた変更は、履歴のために保存される
- 先に `/opsx:verify` を使って問題を見つける

---

<a id="opsxbulk-archive"></a>
### `/opsx:bulk-archive`

完了した複数の変更を一度にアーカイブします。変更間の仕様の競合を処理します。

**構文:**
```
/opsx:bulk-archive [change-names...]
```

**引数:**
| 引数 | 必須 | 説明 |
|----------|----------|-------------|
| `change-names` | いいえ | アーカイブする特定の変更（指定しない場合は選択を促される） |

**動作:**
- 完了したすべての変更を一覧表示する
- アーカイブする前に、各変更を検証する
- 変更間の仕様の競合を検出する
- 実際に実装されている内容を確認して、競合を解決する
- 時系列順にアーカイブする

**例:**
```
You: /opsx:bulk-archive

AI:  完了した変更が3件見つかりました。
     - add-dark-mode (8/8 タスク完了)
     - fix-login-bug (3/3 タスク完了)
     - update-footer (2/2 タスク完了)

     仕様の競合を確認しています...
     ⚠ add-dark-mode と update-footer は、どちらも specs/ui/ に触れています

     コードベースを調べて解決します...
     どちらの変更も実装済みです。時系列順にマージします。
     1. add-dark-mode (1月20日に作成)
     2. update-footer (1月22日に作成)

     3件の変更をすべてアーカイブしますか？

You: はい

AI:  ✓ add-dark-mode をアーカイブしました
     ✓ fix-login-bug をアーカイブしました
     ✓ update-footer をアーカイブしました
     仕様のマージ順: add-dark-mode → update-footer
```

**ヒント:**
- 並行する作業の流れに適している
- 競合の解決はエージェント的（コードベースを確認する）
- 変更は作成順にアーカイブされる
- 仕様の内容を上書きする前に確認する

<a id="opsxonboard"></a>
### `/opsx:onboard`

OpenSpec のワークフロー全体を通したガイド付きのオンボーディングです。実際のコードベースを使った、インタラクティブなチュートリアルです。

**構文:**
```
/opsx:onboard
```

**動作:**
- 完全なワークフローのサイクルを、説明を交えながら案内する
- コードベースをスキャンして、実際の改善の機会を探す
- 実際の成果物を持つ、本物の変更を作成する
- 実際の作業（小さく安全な変更）を実装する
- 完了した変更をアーカイブする
- 各ステップを、その実行中に説明する

**フェーズ:**
1. ようこそとコードベースの分析
2. 改善の機会を見つける
3. 変更を作成する（`/opsx:new`）
4. 提案を書く
5. 仕様を作成する
6. 設計を書く
7. タスクを作成する
8. タスクを実装する（`/opsx:apply`）
9. 実装を検証する
10. 変更をアーカイブする
11. まとめと次のステップ

**例:**
```
You: /opsx:onboard

AI:  OpenSpec へようこそ！

     あなたの実際のコードベースを使って、ワークフロー全体を一通りご案内します。
     小さな改善点を見つけ、そのための適切な変更を作成し、実装して、
     アーカイブします。

     改善の機会がないか、コードベースをスキャンしてみます...

     [コードベースを分析する]

     取り組めそうなものがいくつか見つかりました。
     1. お問い合わせフォームに入力検証を追加する
     2. 認証フローのエラーメッセージを改善する
     3. 非同期ボタンにローディング状態を追加する

     どれに興味がありますか？（他の提案でも構いません）
```

**ヒント:**
- ワークフローを学ぶ新規ユーザーに最適
- おもちゃの例ではなく、実際のコードを使う
- 残しても破棄してもよい、本物の変更が作成される
- 完了までに15〜30分かかる

<a id="command-syntax-by-ai-tool"></a>
## AI ツール別のコマンド構文

AI ツールによって、コマンドの構文は少しずつ異なります。お使いのツールに合った形式を使用してください。

| ツールのコマンドファイル | 構文の例 | ツールの例 |
|--------------------------|----------------|---------------|
| `.../commands/opsx/<id>.*` | `/opsx:propose`, `/opsx:apply` | Claude Code, Gemini CLI, Crush |
| `.../opsx-<id>.*` | `/opsx-propose`, `/opsx-apply` | Cursor, Devin Desktop, Copilot (IDE), Trae, Oh My Pi |
| なし — スキルのみ | `/openspec-propose`, `/openspec-apply-change` | CodeArts, ForgeCode, Hermes, MiniMax Code, Mistral Vibe, Zed Agent, 共有 `.agents` |
| なし — Kimi Code | `/skill:openspec-propose` | Kimi Code |
| なし — Codex CLI | `$openspec-propose` | Codex |

> **Devin Desktop と Devin Local の違い:** `.devin/workflows/opsx-*.md` ファイルにより、
> Devin Desktop では `/opsx-propose` が使えます。Devin Local にはワークフローがないため、
> OpenSpec が `.devin/skills/` に書き込むスキル（例: `/openspec-propose`）を使用してください。
> これは両方のエージェントで動作します。

意図はツールを問わず同じですが、コマンドの表示のされ方は連携ごとに異なる場合があります。[呼び出し方](supported-tools.md#how-to-invoke) に対応しているすべてのツールが一覧されています。この表は、それぞれの形式の例のみを示しています。

> **注:** GitHub Copilot のコマンド（`.github/prompts/*.prompt.md`）は、IDE 拡張機能（VS Code、JetBrains、Visual Studio）でのみ利用できます。GitHub Copilot CLI は現在、カスタムプロンプトファイルに対応していません。詳細と回避策については、[対応ツール](supported-tools.md) を参照してください。

<a id="legacy-commands"></a>
## レガシーコマンド

これらのコマンドは、古い「すべて一度に」のワークフローを使用します。引き続き動作しますが、OPSX のコマンドを推奨します。

| コマンド | 動作 |
|---------|--------------|
| `/openspec:proposal` | すべての成果物（proposal、specs、design、tasks）を一度に作成する |
| `/openspec:apply` | 変更を実装する |
| `/openspec:archive` | 変更をアーカイブする |

**レガシーコマンドを使うタイミング:**
- 古いワークフローを使用している既存のプロジェクト
- 成果物を段階的に作成する必要がない、単純な変更
- 「すべてか無か」のアプローチを好む場合

**OPSX への移行:**
レガシーな変更は、OPSX のコマンドで続行できます。成果物の構造には互換性があります。

<a id="troubleshooting"></a>
## トラブルシューティング

<a id="change-not-found"></a>
### 「Change not found」

コマンドが、どの変更に取り組むべきかを特定できませんでした。

**対処法:**
- 変更名を明示的に指定する: `/opsx:apply add-dark-mode`
- 変更フォルダが存在することを確認する: `openspec list`
- 正しいプロジェクトディレクトリにいることを確認する

<a id="no-artifacts-ready"></a>
### 「No artifacts ready」

すべての成果物が、完了しているか、足りない依存関係によってブロックされています。

**対処法:**
- `openspec status --change <name>` を実行して、何がブロックしているかを確認する
- 必要な成果物が存在するかを確認する
- 不足している依存先の成果物を先に作成する

<a id="schema-not-found"></a>
### 「Schema not found」

指定されたスキーマが存在しません。

**対処法:**
- 利用可能なスキーマを一覧表示する: `openspec schemas`
- スキーマ名の綴りを確認する
- カスタムの場合は、スキーマを作成する: `openspec schema init <name>`

<a id="commands-not-recognized"></a>
### コマンドが認識されない

AI ツールが OpenSpec のコマンドを認識しません。

**対処法:**
- OpenSpec が初期化されていることを確認する: `openspec init`
- スキルを再生成する: `openspec update`
- `.claude/skills/` ディレクトリが存在することを確認する（Claude Code の場合）
- 新しいスキルを読み込ませるため、AI ツールを再起動する

<a id="artifacts-not-generating-properly"></a>
### 成果物が正しく生成されない

AI が、不完全な、または誤った成果物を作成します。

**対処法:**
- `openspec/config.yaml` にプロジェクトのコンテキストを追加する
- 特定のガイダンスのために、成果物ごとのルールを追加する
- 変更の説明に、より多くの詳細を記述する
- より細かく制御するため、`/opsx:ff` の代わりに `/opsx:continue` を使う
