# コア概念の概要

**OpenSpec は、あなたと AI の間にある軽量な合意のレイヤーです。** 変更が何をすべきかをあなたが書き留め、AI が詳細を下書きし、あなたと AI が同じ計画を見て、それからはじめてコードが書かれます。このページは、全体の考え方を1画面にまとめたものです。詳しく知りたい場合は、[概念](concepts.md) をご覧ください。

アイデアの全体像は、この一言に尽きます。**まず合意し、それから自信を持って作る。**

<a id="the-five-ideas"></a>
## 5つの考え方

OpenSpec のすべては5つの概念から成り立っています。これらを理解すれば、あとは細部です。

**1. 仕様が真実である。** 仕様は、システムが*現在*どう振る舞うかを記述します。`openspec/specs/` にあり、ドメイン（`auth/`、`payments/`、`ui/`）ごとに整理されます。仕様は、要件（「システムは30分後にセッションを失効させなければならない（SHALL）」）とシナリオ（given/when/then の具体例）で構成されます。仕様は、「このソフトウェアは何をするのか？」という問いに対する、合意された唯一の答えと考えてください。

**2. 変更は作業の1単位である。** 振る舞いを追加、変更、削除したいときは、変更を作成します。これは `openspec/changes/` 内のフォルダで、その作業に関するすべてを1か所にまとめます。提案、設計、タスクリスト、そして仕様の編集です。1つの変更が1つのフォルダ、1つの機能に対応します。

**3. デルタ仕様は、世界全体ではなく、何が変わるかを記述する。** 変更の中で、仕様全体を書き直すことはしません。小さなデルタを書きます。この要件を `ADDED`（追加）、あの要件を `MODIFIED`（変更）、この別の要件を `REMOVED`（削除）。これが、OpenSpec がゼロからの開発だけでなく既存システムの編集にも優れている秘訣です。到達点ではなく、差分を記述するのです。

**4. 成果物は互いの上に積み上がる。** 変更にはいくつかのドキュメントが含まれ、自然な順序で作成され、それぞれが次のものに情報を提供します。

```text
proposal ──► specs ──► design ──► tasks ──► implement
   理由        内容       方法       手順       実行
```

どれもいつでも見直せます。これらは実現するための手段であって、関門ではありません。（詳しくは後述します。）

**5. アーカイブは、変更を真実に統合し戻す。** 作業が完了したら、変更をアーカイブします。デルタ仕様はメインの仕様にマージされ、変更フォルダは日付スタンプ付きで `changes/archive/` に移動されます。これで仕様は新しい現実を記述するようになり、次の変更に進む準備が整います。サイクルが閉じます。

<a id="the-picture"></a>
## 全体像

```text
┌─────────────────────────────────────────────────────────────────┐
│                          openspec/                              │
│                                                                 │
│   ┌──────────────────┐         ┌──────────────────────────┐    │
│   │     specs/       │         │        changes/          │    │
│   │                  │ ◄─────  │                          │    │
│   │ 信頼できる       │ アーカイブ│ 変更ごとに1フォルダ      │    │
│   │ 唯一の情報源     │ 時に    │ proposal · design ·      │    │
│   │ 現在の仕組み     │ マージ  │ tasks · delta specs      │    │
│   └──────────────────┘         └──────────────────────────┘    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

フォルダは2つです。`specs/` は真実であるもの、`changes/` はあなたが提案しているものです。アーカイブは、提案を真実へと移します。

<a id="the-loop-youll-actually-run"></a>
## 実際に回すループ

デフォルトの設定では、1日の流れは次のようになります。必要に応じて先に考えをまとめ、1つのコマンドが計画を下書きし、あなたがそれを読み、次のコマンドが実装し、最後のコマンドが整理して保管します。

```text
/opsx:explore                   →  （任意）まず AI と一緒に考えをまとめる
/opsx:propose add-dark-mode     →  AI が提案、仕様、設計、タスクを下書きする
        （あなたが計画を読み、調整する）
/opsx:apply                     →  AI が実装し、タスクにチェックを付ける
/opsx:archive                   →  仕様が更新され、変更がアーカイブされる
```

**迷ったら、探索から始めましょう。** `/opsx:explore` はリスクのない思考パートナーです。コードを読み、選択肢を示し、曖昧なアイデアを、コードを書く前に具体的な計画に変えます。曖昧な指示から*何か*を作ってしまう AI への、最良の対策です。何がしたいかを正確にわかっているなら、直接 `/opsx:propose` に進んでください。どちらの場合も、探索はデフォルトのプロファイルに含まれているので、いつでも使えます。[探索ガイド](explore.md) を参照してください。

これらはスラッシュコマンドで、AI アシスタントのチャットに入力します。セットアップ（`openspec init`）はターミナルで行います。この区別が初めてなら、まず [コマンドの仕組み](how-commands-work.md) を読んでください。最もよくある混乱のポイントです。

<a id="enablers-not-gates"></a>
## 「関門ではなく、手段」

この言い回しは OpenSpec のあちこちに登場するので、平易な言葉で説明します。

従来型の仕様プロセスはウォーターフォールです。計画を終えて、*それから*実装が許され、戻るのは大変です。OpenSpec はそれを拒否します。`proposal → specs → design → tasks` という順序が示すのは、次に何が*可能になる*かであって、次に何を*強制される*かではありません。

実装中に設計が間違っていたとわかった？ `design.md` を編集して続けてください。スコープを縮小すべきだと気づいた？ 提案を更新してください。何もロックされません。依存関係があるのは、AI が必要な文脈を持てるようにするためであり（根拠となる仕様がなければ良いタスクは書けません）、あなたを枠にはめるためではありません。

ここでの強みは誠実さです。実際の作業は雑然としていて反復的であり、OpenSpec はそれをそのまま許容します。代わりに規律が求められます。何も強制的に先へ進めないため、変更を散漫に広げず、焦点を保つのはあなたの責任です。[ワークフロー](workflows.md) ガイドに、そのための良い習慣が載っています。

<a id="why-this-is-worth-the-small-overhead"></a>
## わずかなオーバーヘッドに見合う理由

正直に言うと、OpenSpec は手順を1つ増やします。構築する前に、短い計画を書くことになります。では、その見返りは何でしょうか。

- **方向違いを、コストがかかる前に発見できる。** 1段落の提案の中で誤解を直すのはタダ同然です。AI が400行書いたあとでは、そうはいきません。
- **計画とコードが同じリポジトリに残る。** 半年後、仕様がシステムの現在の姿の理由を、あなたと次の AI セッションに教えてくれます。
- **変更をレビューできる。** 変更フォルダはひとまとまりのパッケージです。提案を読み、デルタにざっと目を通し、タスクを確認する。チャット履歴を発掘する必要はありません。
- **既存のコードベースにも合う。** デルタのおかげで、5万行のアプリへの変更を、全体をドキュメント化することなく仕様化できます。

そして正直なトレードオフ: 本当に些細な1行の修正には、この手順が見合わないこともあり、それで構いません。OpenSpec は軽量に設計されていますが、無料ではありません。合意が重要な場面で使ってください。曖昧に頼んだことを自信満々に作ってしまう AI と作業する場合、それはほとんどの場面に当たることがわかるでしょう。
